# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-user, local-only desktop app that tracks which JIRA tickets were worked on with AI assistance. It scans Claude Code session transcripts (and accepts manual entries), infers ticket keys, enriches them from JIRA (read-only), and visualizes the relations with charts. Photino.NET host (.NET 10) + OS-native WebView + vanilla-JS frontend + SQLite. No server, no team sync, no Electron.

## Commands

```bash
dotnet run                              # launch the app (Photino window)
dotnet build                            # build only
dotnet run -- --scan                    # headless: run the transcript scanner, print counts
dotnet run -- --sql "SELECT ..."        # headless: read-only query (PRAGMA query_only=ON enforced)
dotnet run -- --set <key> <value>       # headless: write a Settings row (use jira_token for the DPAPI-protected token)
dotnet run -- --route <page>            # open the app directly on a page (dashboard|sessions|manual|tickets|livecode|settings) — used for headless UI verification; also accepts a param, e.g. --route "session/<sessionId>" for the session detail page
dotnet run -- --detailtest <sessionId>  # headless: print the session-detail deep re-parse (per-tool/per-model/timing), as fed to the detail page
dotnet run -- --pty-test                # headless: spawn a pseudo-console and verify continuous output streaming (Live Code terminal)
dotnet run -- --envtest                 # headless: verify ANTHROPIC_API_KEY is stripped from a session's child env
dotnet run -- --shelltest               # headless: print resolved PowerShell / Git Bash executables
dotnet run -- --accounttest             # headless: print subscription plan + usage-reset date from ~/.claude.json

# Publish the single-file, self-contained exe (see PROGRESS.md for the deliverable path):
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -p:DebugType=none -p:DebugSymbols=false
```

There is no test project — verification is done via the `--scan`/`--sql`/`--route`/`--pty-test`/`--envtest` CLI verbs and window screenshots.

Packages: Photino.NET, Microsoft.Data.Sqlite, System.Security.Cryptography.ProtectedData, SQLitePCLRaw.bundle_e_sqlite3, **Porta.Pty** (ConPTY wrapper for the Live Code terminal; managed-only, so the single-file publish is unaffected).

## Architecture

**Message bridge.** The WebView and .NET communicate over Photino's string message bus as JSON. Request `{ id, action, payload }` → response `{ id, ok, data | error }`. `Bridge/MessageRouter.cs` parses, dispatches by `action` to a registered handler on a pool thread, and serializes the reply (camelCase). Frontend side is `wwwroot/js/bridge.js` — `Bridge.call(action, payload, timeoutMs)` returns a Promise; pass `timeoutMs: 0` for unbounded operations (e.g. JIRA sync, Excel export) so the client doesn't strand a still-running backend call.

The bridge also has an **unsolicited event channel** for streaming (used by the Live Code terminal): `MessageRouter.PushEvent(event, data)` sends `{ type:"event", event, data }` with no request id, and the frontend subscribes via `Bridge.on(event, handler)`. Regular request/response is unchanged.

**Handlers** live in `Bridge/Handlers/*.cs`, each with a static `Register(router)` called from `Program.cs`. **Critical trap** (documented in `SessionHandlers.Register`): synchronous handlers must run inline and return `Task.FromResult<object?>(...)`. Do NOT wrap the body in `Task.Run(() => { ...; return null; })` — it binds to the `Func<Task<object?>>` unwrap overload, and unwrapping a null task yields a *canceled* task, surfacing as a spurious "A task was canceled" error even though the DB write committed. `MessageRouter.OnMessage` already provides the pool thread.

**Scanner pipeline** (`Scanner/`): `TranscriptScanner` walks `%USERPROFILE%\.claude\projects\**\*.jsonl` (append-only JSONL), incrementally by remembered byte offset (`ScanState` table); it reads only complete lines (stops before a partial trailing line a writer may still be appending) and uses `BEGIN IMMEDIATE` transactions so concurrent scanners (even other processes) don't double-count. Counters are **additive** across incremental parses; a shrunk/rewritten file triggers a full reparse that first zeroes counters. → `SessionAggregator` is the **ONLY** place that knows the undocumented Claude Code transcript schema — put all format-drift fixes here; unknown/malformed lines are skipped, never fatal. → `TicketKeyInferrer` extracts ticket keys with source priority **branch → cwd → prompt_text**, filtered by a project-key allowlist. Sidechain/subagent transcripts (in session-named subdirs) are skipped in v1. Alongside the token counters, the scanner also refreshes each changed file's **`ToolUsage`** rows — per-session sub-agent / skill / MCP-server / hook counts from a full-file parse (`SessionAggregator.ReadToolUsage` → `ToolUsageRepo.ReplaceForFile`, **set** semantics, decoupled from the incremental token counting). This powers the dashboard's **Automation & extensions** charts (`stats.dashboard` → `agentUsage`/`skillUsage`/`mcpUsage`/`hookUsage`). The v6 migration flags a one-time backfill (`toolusage_backfill_pending`) so sessions scanned before this table existed get populated on the next scan.

**Data layer** (`Data/`): raw ADO.NET via `Microsoft.Data.Sqlite`, no ORM. `Db.Open()` sets WAL + foreign_keys. `Migrations.cs` is idempotent (`CREATE TABLE IF NOT EXISTS` + `AddColumnIfMissing` for post-ship columns), seeds `ActivityCategories`, and stamps `SchemaVersion` (currently 6). Repositories in `Data/Repositories/`. **DB location is portable-first**: `aiusage.db` next to the exe when that dir is writable (so the whole folder is copyable), falling back to `%APPDATA%\AIUsage\` only under Program Files; an existing %APPDATA% DB is copied over once (with `-wal`/`-shm`).

**Frontend** (`wwwroot/`): classic scripts + globals — **no ES modules** (they don't load over `file://` in WebView2). `app.js` is a hashchange router; each view self-registers on `window.Views` (`window.Views.<name> = ...`) and exposes `render(container, param)`. The hash may carry one param after the first `/` — `#session/<id>` routes to the `session` view with `param = <id>`; the router maps the `session` route back to the "Sessions" sidebar item for highlighting. The **Sessions list → detail** flow uses this: each row title links to `#session/<id>`, and `session.js` renders a detail page (Overview / Tools / Models / **Agents & extensions** / Token cost / Tickets) from `sessions.detail`, which re-parses that one transcript on demand (`SessionAggregator.ReadDetail`) for the exact per-tool + per-model breakdown, reply/tool-call counts, an Agent/Active/Idle time split, and the sub-agents/skills/hooks used (agents ← Agent/Task `subagent_type`, skills ← Skill `skill`, hooks ← `hook_success`/`hook_error` attachment lines, MCP tools ← the `mcp__…` tool names) — none of which the list/DB stores; token **cost** is derived in the view from a model-family `$/Mtok` rate table. Shared helpers live on `window.App` (`toast`, `esc`, `fmtNum`, `fmtDate`, `refresh`, `exportExcel`). Chart.js is **vendored** at `wwwroot/lib/chart.umd.js` (no CDN — corporate network blocks it and the app runs offline). Dashboard charts use a fixed category→color palette (color follows the activity category, not its rank).

**Embedded web assets** (`WebAssets.cs`): `wwwroot/**` is compiled in as embedded resources (`LogicalName=web/...`) so the published exe is one self-contained file. On startup they're extracted to `%LOCALAPPDATA%\AIUsage\web` and loaded over `file://` (keeps `crypto.randomUUID` working). **Extraction overwrites on every launch**, so editing `wwwroot` and re-running (or re-launching the exe) picks up changes. Dev fallback: on-disk `wwwroot` next to the exe if no embedded resources.

**JIRA** (`Jira/`): read-only JIRA Cloud REST. Token is DPAPI-protected at rest (`SettingsStore.SetProtected`, `dpapi:` prefix; non-Windows falls back to `plain:`) and write-only in the UI. The DPAPI token does NOT survive copying the folder to another machine/user — it degrades to "not set" by design. Fetches are lazy/background on link creation (`JiraSync.TryFetchInBackground`). **Never paste a real JIRA token into Claude** — use `--set jira_token` or the Settings UI. `FetchIssueAsync` also fetches the description and flattens the ADF (Atlassian Document Format) tree to plain text.

**Live Code page** (`Terminal/`, `Bridge/Handlers/LiveCodeHandlers.cs`, `wwwroot/js/views/livecode.js`): interactive Claude Code sessions embedded in the app — **multiple concurrent sessions, one per UI tab**. Each tab is identified by a frontend-minted `tabId` (a GUID, stable across the tab's Stop→Resume/Reset), and the backend keeps a `Dictionary<tabId, LiveSession>` (replacing the old singleton). `ConPtySession` hosts a shell in a pseudo-console — via the **Porta.Pty** library, NOT raw ConPTY: a hand-rolled `CreatePseudoConsole` implementation ran the child fine but conhost wouldn't stream output continuously on this Windows build (only flushed on resize/close), so we use the library (see PROGRESS.md). Output bytes stream to the WebView over the event channel as `pty.output` (each event tagged with its `tabId`) and render in **xterm.js** (vendored at `wwwroot/lib/xterm.*`, same no-CDN constraint as Chart.js); one xterm per tab, all in a persistent container with only the active tab shown, and a single subscription routes events by `tabId`. Keystrokes go back via `pty.input` (also carrying `tabId`). Every per-session action (`start`/`resume`/`reset`/`stop`/`closeTab`/`attach`/`metrics`, `pty.*`) requires a `tabId`. On start, the chosen shell (`ShellResolver`: PowerShell, or Git Bash with fallback) is spawned in the selected folder, then a `claude …` command is *typed in* to work the selected ticket (built in `BuildClaudeCommand`, flattened to one line + shell-quoted). `ANTHROPIC_API_KEY` is stripped so Claude Code uses subscription auth (Porta.Pty inherits the parent env and ignores dict removal, so `ConPtySession` also unsets the var in this process). Confirmations: `--permission-mode acceptEdits` (auto-approve, behind a warning confirm) or `bypassPermissions` (behind a danger confirm), plus a best-effort `PromptWatcher` that injects Enter on detected prompts. Starting a session with a ticket **auto-links** it (`SessionRepo.LinkLiveCodeSession`, source `livecode`) so the work is captured. On open, the page checks the CLI is installed (`Terminal/ClaudeCli`) and warns if not. The shared ticket picker at the top lists the user's most-recently-updated assigned tickets (finished statuses excluded); how many it shows is configurable in **Settings → Live Code** (`livecode_ticket_count`, default 3, clamped 1–20; surfaced to the page via `livecode.config`'s `ticketCount`), and a **↻ Re-fetch** button beside the list reloads them from JIRA on demand (`livecode.tickets` always hits JIRA live). Agents: the dropdown lists `.claude/agents` (project + user); a **Custom Agent** file picker installs a chosen `.md` into `.claude/agents` and the kickoff becomes "Use the &lt;agent&gt; agent to work on &lt;ticket&gt;" (prompt-based, no `--agent`). Selecting an Agent from the dropdown clears + disables the Custom Agent input (the two are mutually exclusive; `refreshControlLocks` is the single locking authority). A **Resume Sessions** button (beside Browse) lists the chosen folder's existing Claude Code sessions (`livecode.sessionsInFolder` → `Scanner/FolderSessions.cs`, labelled by each transcript's first user prompt via `SessionAggregator.FirstUserPrompt`); picking one resumes it interactively (`livecode.resumeSession` → `claude --resume <id>`, no prompt) in the active tab (confirm-replace if running) and locks Shell/Model/Custom Agent until it stops. The button is disabled when the folder has no sessions. Each tab has its own compact "this session" tokens/context readout (`livecode.metrics {tabId}`, polled for the active tab); the session **Tokens** figure is `input + output` **including sub-agents** — the SAME formula as the dashboard and `weekTokens` (so the numbers stay consistent across the app), just with sub-agent usage added. Cache is shown **separately** as a **Cache** field (`cache_creation + cache_read`, with a "created … · read …" tooltip) so it never inflates the headline Tokens number. Task-tool sub-agents write to `<sessionId>/subagents/agent-*.jsonl` sidechains that the scanner skips, so `SessionAggregator.SubagentTokens` returns their in+out and cache split (`SubagentUsage`) and the handler adds both (Tokens returned split as `mainTokens`/`agentTokens`; cache as `cacheTokens`/`cacheCreation`/`cacheRead`). The sub-agent re-add is display-only for this readout — the DB/dashboard/`weekTokens` still exclude cache and sub-agents (v1 design). The dashboard and `weekTokens` count `input + output` only (all cache excluded). The shared bottom panel keeps the plan, week tokens, two rolling **usage-limit bars** (SESSION = 5-hour window, WEEK = 7-day window), and the top-5 active Claude Code sessions (`Scanner/ActiveSessions`). The usage bars come from `Platform/ClaudeUsage.cs` → `livecode.usage`: a GET to Anthropic's `oauth/usage` endpoint (the same data as Claude Code's `/usage`), authed with the access token from `~/.claude/.credentials.json` (token used only to sign the request, never stored/logged), returning server-computed `utilization` percents + reset times (no local quota math). It's cached 5 min and best-effort (bars hide when signed out/offline); the page polls every 60s and colours a bar amber ≥80% / red ≥95%. Tabs (and their sessions) survive navigation: `tabs[]` lives in the view closure, `ConPtySession` keeps a per-tab rolling output buffer, and on return the page reconciles with `livecode.list` and `livecode.attach {tabId}` replays each running tab's buffer into a fresh xterm (the router wipes the DOM but not the backend sessions). **Stop** (`livecode.stop {tabId}`) kills the process tree but keeps the entry so Resume works; **closing a tab** (`livecode.closeTab {tabId}`, confirmed if running) disposes and drops the entry; **Resume** re-launches `claude --resume <id> 'continue'`; **Reset** sends `/exit` then restarts a fresh Claude session on the same ticket (shared `StartTicketSession`). New tabs inherit last-used defaults; soft cap of 6. The sidebar dot (app.js polls `livecode.running` → `{running,count}`) is green when any session runs, red when none; hovering the nav item shows a popover listing live tabs (`livecode.list`), and clicking a row focuses that tab. The active-sessions list polls a scan-free `livecode.activeSessions` every 2s. **Same-folder safeguard**: on Start, if another running tab is already working in the chosen folder, the page shows a warning (concurrent agents on one folder can corrupt edits — "own risk") with a git-repo-aware 3-way choice (`App.choose`): **isolated worktree** / continue in same folder / cancel. Choosing worktree passes `isolation:"worktree"` to the backend, which runs `GitWorktree.Create` (`Terminal/GitWorktree.cs`) — a new branch `livecode/<ticket>-<hex>` in a sibling `<repo>-worktrees/…` folder — and launches the session there (transcript + auto-link use the worktree cwd; `livecode.folderInfo` reports whether a folder is a git repo). Reset reuses the tab's worktree; **closing** a worktree tab removes it only if clean (`TryRemoveIfClean`: no uncommitted changes and no unmerged commits), else keeps it. Isolated tabs show a `⑂` marker.

## Conventions & gotchas

- **`net10.0`**, nullable + implicit usings enabled. Namespaces mirror folders (`AIUsage.Bridge.Handlers`, etc.).
- Ticket keys are validated against `^[A-Z][A-Z0-9]{1,9}-\d{1,6}$` and uppercased. Auto-links carry a `source`; manual/confirmed links are preserved when the allowlist purge runs (`SettingsHandlers.PurgeDisallowedAutoLinks`).
- Headline token figures **exclude cache-read tokens** by design.
- Do NOT use Photino `ShowSaveFile` off the UI thread — it returns null (reports a false "cancelled"). Excel export (`Export/XlsxWriter.cs`, minimal hand-rolled OOXML, no new dependency) saves directly to Downloads and reveals via `explorer /select`.
- The startup background scan only re-renders the input-free dashboard, never a view the user may be typing into (re-render wipes form state via `innerHTML`).
- **ConPTY streaming**: use `Porta.Pty`, not raw `CreatePseudoConsole` — the raw path doesn't stream continuously on this machine (see the Live Code paragraph). Stripping a child env var also unsets it in the app process (Porta.Pty inherits parent env); only `ANTHROPIC_API_KEY` is stripped today, which the app never reads.
- Claude Code encodes a session's cwd into its `~/.claude/projects/<name>` folder by replacing `:`, `\`, `/` with `-`. Live Code launches `claude --session-id <guid>` so `FindActiveTranscript` reads exactly `<guid>.jsonl` — matching by "newest file in the dir" is wrong because other concurrent Claude Code sessions (even this one) write to the same folder.
- Git Bash is resolved from the Git-for-Windows install paths, **never** a bare `bash.exe` on PATH — on Windows that's `C:\Windows\System32\bash.exe` (the WSL launcher), which fails with `execvpe(/bin/bash)` when there's no distro (`ShellResolver.IsSystemShim`).
